日期：2026-10-11。按用户要求继续实质研发，记录问题和修复；**本轮不提交、不推送**。本文供之后用户命令推送时的 GPT Pro 审核使用，不代表整个项目或 TRE/CIE 质量目标已验收。

## 1. 本轮解决的问题及适用边界

旧业务入口把早包展开为两个运输任务，不能证明同一个业务袋实际入库、保留托盘并最终完成。本轮新增不可变业务输入、显式运行代理合同、持盘存储约束、必经存储节点的完整路径搜索及实际入/出库事件。

每个业务袋保留最终目的地。`StorageBag` 使用公开固定的 waypoint/release；同一个实体托盘随袋经过存储、等待、出库，直到最终卸载才完成业务并释放盘。`StorageSnapshot` 保存实际入/出库进度；普通 `Bag`/`Snapshot` 结构不改，以保持旧普通任务的内容哈希和恢复语义。库位使用既有有限可等待节点容量，装卸/接收仍是显式 `FixedLocalModule` 代理。

**这只是已公告 release、on-carrier、共享节点库位的研究合同。** node53 原角色是空盘库代理，未被证实为现场 EBS。本轮不把它称为真实立库/检索系统；不支持 off-carrier、动态撤销/修订 release、独立检索设备或现场模块授权。原地图、五条跨区连接、所有原始边（包括 97→98 的零容量关闭边）保持。入口 headway、off-carrier、W2 受限信息业务链及 W4 独立来源确认仍需实现，不能用本轮中央代理替代。

## 2. 输入、时钟与完整分母

`business_inputs.py` 从原 timetable、raw、canonical、父源/派生清单和 Round8 全量规范化记录交叉校验。每件业务袋保存源 SHA/原 ID/行号、父源身份、原始十进制秒、航班代理、旧运输段 ID、保护规则和时钟绑定。到达/release 向上量化，截止向下量化；用精确有理数处理超出全局 Decimal 精度的边界。

1× 全部 28506 件（15097 早包、43603 旧段），2× 全部 57012 件（30194 早包、87206 旧段）保留。静态正容量最终 OD 不可达分别 4001/8002 件，仍在分母。两档只来自一个原 timetable，2× 是同源增密；独立观测运营日计数仍为 0。每档只有显式指定的 11 只初盘，不按任务数量造盘。

`business_runtime.py` 先验证完整 BusinessWorkload 内容绑定，再按原 OperationContract 复算保护/截止/早包/release，读取同 SHA 地图生成完整私有环境任务带。初始公共状态不含未来袋或 release 表。任何窗口选择发生在完整验证与适配之后，另存完整 scope，不篡改全源对象。

RuntimeProxyContract 要求显式提供节点容量/等待许可、全部节点分区、空满盘边权限代理、原边容量保留规则、精确 length/speed 时间量化、装卸/hold/接收/库存参数、路由预算与协调开关。当前只支持零时长 FIFO 装载和既有固定模块。缺字段、现场 confirmed 标签或不支持的服务模式拒绝，不隐式填现场数值。

独立输入审计另实现了非连续 ID、高精度 4800 秒阈值、低 Decimal 精度、分目的航班代理、漏袋和错误 SHA 等反例；从原件复算两档共 85518 条时钟及身份链。最终测试/源冻结数在闭合结果中列出。

## 3. 路由、提交和供盘的同一约束

`storage_routing.py` 包装既有 generator。普通袋/空盘原样委托；存储袋使用 `(node,time,visited)` 路径搜索，保持一个最终完整见证，包含 release 下界、实际节点容量和最终卸载截止。没有把存储节点临时改成 Bag.destination，没有两段独立卸载，也没有在 release 时生成新袋或新盘。

每次存储查询重新构建拓扑和两个静态下界，实际预处理工作计入同一 expansion/time 预算；不引入未申报的持久缓存。候选数 K、搜索时域、展开预算沿用显式合同。短时域和预算耗尽不等于不可行，不能将无候选填成成功或无成本。

执行层对新提交、next-edge 的完整 witness、旧路线回退、后缀替换、确定/条件供给实施同一存储约束。替换时，已进入的冻结前缀只在私有 `StoragePlanningSnapshot` 推导预期入库进度，真实状态不前移；实际提交重新绑定原状态和冻结前缀。私有规划视图不能作为物理 Snapshot 运行或提交。

实际事件包括同 tick 入库/出库。引擎用已进入腿游标证明到达，先记录实际 ingress，再处理出发；不能从将来计划伪造已经入库。入库和驻留不产生空盘信用；完整合法最终路线的供给时刻包括 release、余程、最终卸载及 hold。条件预测携带存储合同依赖，但仍不授予导出权限。

当前 W2 分区消息和独立 joint/atomic 参考内核未建模这些状态，因此在初态、未来任务、检查点恢复/规划入口显式拒绝 Storage 合同，防止降格成普通 Bag。通用原子提交使用共同 validator，并有独立反例覆盖。

## 4. 发现的缺陷与修复记录

独立审计以手写路线构造反例，未依赖新 generator 的正确性，发现并保留了以下真实失败：

1. 托盘实际在 A，却给旧计划填 S→D，就能产生 D 的确定供给。补路线连续性和当前物理位置匹配。
2. 在 now 之后回填过去 A→S 的腿，能假装已经入库。过去的存储进出必须匹配实际 milestone。
3. 真实旧在途最终到达形成 zero-leg 卸载计划后，篡改 unload/usable 可提前供盘。补最终模块时钟、hold 及正在服务的托盘 available_at 一致性。
4. 手工预装违反保护截止的完整旧计划未被供给入口拒绝。补最终保护截止复验。
5. 旧完整计划可以在不可等待节点隐藏腿间等待。补历史腿和当前等待许可。
6. 旧已进入的直达最终边可以绕过 mandatory storage，并提前公布最终供给。补 old_in_transit 的实际 storage departure 前置证据。
7. 托盘位置为存储节点但没有真实 ingress 时，旧计划入口比新提交宽松。统一要求实际记录；合法初始化/装载时由物理观察生成记录。

输入适配另发现：冻结 dataclass 仍可通过 `dataclasses.replace` 构造篡改任务，再沿用原源 SHA。增加全内容 SHA 并复算合同语义，拒绝改保护/截止/生命周期后伪称原输入。内容哈希是防意外修改和审计绑定，不声称密码学权限系统。

作者自身错误也保留：生命周期 fixture 的 cache 参数名、isolated cache 与 wall deadline 冲突、把实例误传为 factory；这些都在新增物理运行前失败，后续使用正确原接口，没有放宽断言。独审首次 runner 引用不存在的测试文件及接收 hold 冲突 fixture 的失败也单独保留。

## 5. 机制与完整窗口实验

固定十类机制覆盖单盘复用、两盘、满库竞争、零等待、晚入库、release 超时域、保护截止不可满足、关闭入库边、关闭回流边及源点在存储。每类分别运行 whole_route/next_edge，并在 tick1/8 保存和恢复。原矩阵中的保护任务按既有政策保持完整承诺，因此不把两种模式标签误当真正分段路线证据；额外固定 unprotected_reuse 才检查自动分段继续。

单盘手算例中，同一只盘依次完成两件早包和一件直接袋，最终完成 tick9/18/24，实际空盘回流两次，总空行驶 4 ticks。长 release=100 的例子，horizon80 初期无候选但不丢袋，后续合法完成 103/112/118。关闭边及不可满足保护截止例保留全部三件业务分母和固定停止时的未完成，不只报完成案例。

`mechanisms_001` 运行 60 次但最初只落了 20 个主原件，40 次恢复只保存布尔结论，独审指出该证据不足。保留 001；`mechanisms_002` 重新运行同一 60 次，保存全部 replay 原件及完整 checkpoint/SHA。`mechanisms_003` 补非保护例 6 次。重复运行不是新增独立场景或运营日。

完整业务窗按**精确原始首到达秒至其后 3600 秒（右开）**固定，无 thinning；这一小时 44 件全部为早包。从 epoch0 按正常事件推进；此前无任务，不跳物理时钟。保留原图 151 节点/227 边、11 初盘、node53 单库位、其余节点容量4、1秒 tick、最终卸载1秒/hold0、接收容量1、两模式共享原边、单中央分区和固定 FIFO/reactive 策略。上述是显式研究代理，未由现场资料确认。

事先声明 h80 与 h21600 两档，其余条件相同；每查询最多10000展开，无 wall deadline，原 isolated cache 合同。合同 candidate_count=4，但未挂 route_selector 的既有默认策略实际向 generator 请求 K=1，这与后面的独立 K4 故障查询不是同一个分母。尾界为窗口最大截止+3600 ticks，每部署另设600 CPU秒/900 wall秒资源上限。资源退出、未完成、已公开但未接纳的保护任务全保留。

## 7. 原图暴露的搜索问题与第二次修复

原图长时域查询并非只受时域限制。保存真实 checkpoint 推进到 tick8876，对 `projected:1x:2` / `proxy-initial-26`，K4、h21600、10000预算：旧搜索0候选，9317次 heap pop 的最终到达下界 f 全为19749。固定 release 把大量不同时间/回路标签压在同一 f 上，FIFO 平局顺序长期无法推进完整 witness。

新路由只把同 f 次序改为“剩余必经静态旅行、是否已访问存储、FIFO”，f 主序、K-label上限、预算、容量、保护及完整 validator 均保持。保存的同一 query state 返回4条合法候选、670展开，原227图边/341反向下界工作完全相同。独审另重跑旧/新，逐 pop 核对主 f 最小，并绕开作者validator手验4条完整 witness 的路径、时钟、容量和 release，最终卸载均19750。单次毫秒耗时只作诊断，Windows CPU=0是量化，不声称零成本或100ms保证。

满库合成反例仍有合法晚到 witness 但在500预算内旧/新都耗尽。只解决了同界展开次序，不能宣称已解决资源日历造成的低下界平原或完整业务吞吐。资料、负例、旧/新原件在 `phase4_round9_storage_release_plateau_20261011/REPAIR_RECORD.md`。已查阅 SIPP 第一方论文，把可用区间、多容量、禁等链、K候选与真实服务边界的下一实现义务写到邻近 `SAFE_INTERVAL_NEXT.md`；该设计尚未实现。
