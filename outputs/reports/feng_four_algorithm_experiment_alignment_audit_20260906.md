## 3. 指标同名并不证明计时阶段相同

本次 `THT(D)` 为每袋的各业务段 `Σ(completion − canonical scheduled D)`；`THT(native)` 则减去各执行器自己的起点。G31 为 admitted/processed attempt，V5 为 first admission，HCA 为成功 planning epoch。三者还不能被视为相同物理进入系统事件。

Feng 文字把 `t_k` 称为进入系统时间，另明确允许规划失败后在连接线等待。原文和现有 Java 并未建立随机 canonical D、实际源放行、首边准入、成功规划与论文统计起点之间的唯一映射。历史工作簿的 shared-D 求和只能支持该原始历史表，不会自动赋予随机 canonical D 相同含义。EBS 两段在当前模型中按独立计划任务运行，允许重叠；这不等于验证了真实早到仓储的入库后才能出库约束。

因此可报告本项目明确操作定义下、附带实现限制的系统观察，不能写成“已按冯精确 THT 证明 G31 全面领先”。带本轮已知 HCA 时间缺陷的既有输出中，原生起点列的 HCA mean/max 在三个具有完整人口时间的场景均低于 G31；共同 D 方向不同，必须同时展示，不能将其中任一方向升级为已修复正确系统的性能结论。2× THT 一律 N/A 是当前冻结协议规则，不能解释成冯论文证明 2× 不允许计算 THT。

截止成功率也有独立映射缺口：CIE p.29、学位论文正文 p.31 要求行李在航班起飞前 45 分钟送达，而当前统计以输入 `STD` 为截止。原 Java 只是读取第三列 `STD(s)`，并将 EBS 出库时间设为 `STD−2700`。还没有输入字段来源证明 STD 本身是否已预扣这 45 分钟。因此可以称当前 `on_time_rate` 为“输入 STD 截止的准时率”，不能直接改称论文故障实验的 success rate；也不能在缺乏证据时擅自再扣 2700 秒。

## 4. 原始 Java 与“正确复现”的层级

原始工程可恢复的是 HCA 的 `Tasks → ICS_PathFinding → Astar` 链，不是 Feng 对比实验中的独立 DH 源码。HCA 的段 ID 修复保留了原路由、预约、源放行和时间推进公式，修复了同袋 EBS 两段覆盖活动路线/预约的问题；它不等于已经修复或证明全部原始算法正确。

本轮直接使用材料包原始 Java 编译构造五节点、无预约、无停留、零启发值夹具，确认 `Astar` 在更短路径更新时只更新 `g/h/f/parent`，没有同步 `t1/t2`。返回路径 `[0,2,3,4]` 的到达时间为 `[0,2,11,12]`，沿返回路径逐边计算应为 `[0,2,3,4]`。该错误发生在原件，正式 HCA 所用 Astar class 与反例的原件编译 class 一致。15 个原始 Java 文件与仓库镜像有 14 个字节完全相同，Astar 仅换行不同，15 个规范文本均相同。

随后对全部正式 HCA 的原生 `routes.csv.gz` 作只读扫描，核验压缩及解压后 SHA，按实际地图节点停留、边长和 2.5 m/s 重算每条返回路径的 `goal T2`：

`expected_goal_T2 = planning_epoch + Σ(全部路径节点 through，包含起点和终点) + Σ(边长/速度)`。

原始无故障 A* 没有显式等待动作，其活动更新分支的偏移为 0；该核对不是 DH 的 2 秒 transfer 模型，也不是拿无拥堵最短路去比较真实绕行路径，而是核对日志中的**同一条已选路径**与原程序时间递推是否自洽。终点 through 已计入；南宁存在 0/1/3 秒终点，省略终点停留的临时初版诊断已废弃，不参与以下统计。

**60/60 格均检出，合计 3,817,428 条计划路线中 1,340,380 条时间不一致。** 分母是已规划的运输段路线，不是原始袋人口；未规划段不在该项检查分母中。例：map2 1×、seed 104729，执行 ID 62，规划 epoch 12471，实际返回路径的节点 through 总和 10 s、边行驶总和 66.8 s，应到 12547.8，导出 finish_time 为 12549.6，相差 1.8 s，终点 through 为 0。

这个结果证明正式批次包含时间不自洽的原始代码输出，但尚未量化修复后最终 THT、吞吐量或排名改变。原生路由表未保存完整中间 `t1/t2`，不能据此计算所有预约冲突或宣称每个差异都导致碰撞。修复会改变预约与后续选路，**不能直接从已保存 THT 减掉差值来伪造修复结果**。本次将该 HCA 版本的“正确性完整验收”结论暂缓，保留它作为忠于原始路由代码但有已知缺陷的观察；此前段 ID 修复及档案字节校验仍是各自范围内的真实结论。

另对正式南宁首个任务 OD `24→53`、epoch 8866 用原类和空预约独立重放，得到与正式 seed 104729、execution ID 1 相同的路径和结束时刻 9073.976，并直接看到三个中间节点的时间递推偏差合计 3.592 秒；因此至少该实际实例无需拥堵等待也能触发。该诊断不冒称重放了全批拥堵环境，见[原类逐节点输出](../evidence/feng_java_consistency_recheck_20260906/nanning_empty_reservation_probe.json)。

## 5. 交付就绪程度与必要收口

现在可以交付有身份、局限与双时钟的三方法无故障扩展观察，以及本次新增的 HCA 时间一致性诊断。HCA 结果须明确标注已发现缺陷，暂不作为“正确实现已验收”的无条件性能证据。尚不能交付“四算法完全复现 Feng、所有场景正确且 G31 全面领先”的结论。

正式论文收口至少需要：

1. 原始 HCA 时间标签缺陷已在全部 60 格中检出。若需要“时间/路径一致的正确 HCA”正式对照，应另冻结修复版、先通过反例及预约回归，再重跑受影响的全部 60 格；不要覆盖本轮原算法观察，不通过重聚合旧结果代替新执行。
2. 为 Tarău 2010 补足共同输入、负荷与种子结果，同时先明确它仍是 P1 路线机制对照还是端到端适配系统。若主张路线机制归因，须保留同执行器、neutral FIFO 的匹配 G31 对照，不能直接拿 G31 native 的另一个配置替代。
3. 把“论文基础验证”和“本项目两图高负荷扩展”分表；若声称完整复现论文科目，需补齐当前实现的速度扫描、动态/静态偏差和固定断链实验。
4. 在操作层统一/校准 THT 起点和截止成功率含义；原件没有识别出的部分明确列为假设，不通过选择有利时钟宣布胜出。
5. 同步投稿稿件。`docs/paper/cie_manuscript_patch_v2.md` 和 `cie_claims_revision_v2.md` 仍引用早期 DH 238.702 s 和旧 HCA 主结论，属于旧协议历史文本，不能直接作为本次结果的最终稿。新报告不会自动改写这些旧文档。

本轮核实只新增原始类最小反例和只读日志检查，不重跑正式矩阵、不改历史文件、不推送结果。详细审计产物与原始数值分开保存。
