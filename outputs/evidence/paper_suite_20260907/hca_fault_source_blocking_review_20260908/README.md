# HCA 故障样本的源端阻塞诊断

只读抽查南宁 1×、2.5 m/s、seed 104729 的 q02 与 q14。两例低完成率与当前原生 HCA 的源端放行策略一致；所查证据未显示进程失败或人口账目丢失。此结论不是对全部种子或全部物理实现的证明。

| 样本 | 原始袋完成 / 28,506 | 完成段 | 未规划段 | 尚未释放段 | 在途路线 | 账目残差 |
|---|---:|---:|---:|---:|---:|---:|
| q02 | 595（2.09%） | 2,451 | 12 | 41,139 | 0 | 0 |
| q14 | 476（1.67%） | 2,240 | 12 | 41,350 | 0 | 0 |

两例均 returncode=0，完整运行 90,000 个 epoch 至 98,259 秒，原生终态为 `HORIZON_REACHED`，stderr 为空。原始袋必须所有业务段完成才计完成，因此“完成段”不等于“完成袋”；两种正式 THT 均保留 NA。

`release.csv` 与 `routes.csv` 的执行 ID 差集各为 12 件，恰覆盖全部 12 个释放源。这些任务也是各来源最后一次释放的任务。对实际地图删除该格全部 `disabled_edges` 后独立做有向 BFS，24 个任务 OD 均无路可达。每件任务的 ID、OD、release 行号、时刻和 BFS 结果见 [verification.json](verification.json)。

代码直接解释了为何影响会扩大：[Tasks.java 第 151 行](../../../../benchmarks/java/hca_paper_suite_v3/App/Tasks.java#L151) 只在同一源没有 `unfinishTasks` 时释放下一件；[ICS_PathFinding.java 第 138–159 行](../../../../benchmarks/java/hca_paper_suite_v3/App/ICS_PathFinding.java#L138) 对找不到路径的任务保留并逐 epoch 重试。因此，无路任务会阻止该源后续任务继续释放。q02/q14 最后释放分别发生在 23,488/21,710 秒，最后实际完成事件分别在 23,808/21,878 秒；此前成功规划的段全部完成，之后源端阻塞仍持续至固定截止时刻。

相同输入与禁用边集合下，G31 这两个样本分别完成 25,886（90.81%）和 25,193（88.38%）件。**该系统级差距包含不可达任务处理和源端放行策略差异，不能把巨大的相对吞吐提升全部解释为纯路径选择优势。** 本次没有重新审计 G31 的大原生档案。`source_backlog_area_seconds` 还包含 EBS 调度间隔，不应全部称为物理排队时间。

本次仅读取小日志、状态、源码及约 150 KB 地图，没有重跑仿真、解压大档案或更改旧结果。JSON 保存两样本所读文件 SHA、源码行锚点和核查边界；完整原始袋计数引用现存人口审计，本次未重新扫描大生命周期文件。
