# 南宁 1×：原生 Java 无显式线路存储容量抽象下的 G31 比较

日期：2026-10-23。

**G31 在本次南宁 1× 对照中仍有优势；新评分带来了小幅增益，不能把原有优势都归因于这次修改。** 在使用同一组 Java 实际任务释放时刻后，原生 Java HCA 的平均运输段耗时为 292.92 秒，旧 G31 为 224.23 秒，纯日历候选为 223.31 秒。候选比 HCA 低 23.77%，比旧 G31 低 0.41%。保留 `legacy` 为默认模式，候选通过显式开关启用。

## 撤销与本轮改动

上一轮新增的物理执行器已撤销，源码及实验记录保留在旧实验目录 `withdrawn_source/`。先将当时改动的原文件逐字节恢复至工作树基线 `9f23c25a631786ad4c1f47c442d72dcfb3ac098f`，再进行本轮修改。参见 [撤销回执](rollback_receipt.json)。旧报告已标记为撤销方案的历史记录。

本轮直接修改成熟 G31 的评分分支，保留逐跳选路、服务预约、J2 合流仲裁、PIBT 执行授权、源端策略和恒速行程。**不增加线路容量、有限节点缓存或满载回压，不改变基础服务时间；不修改空托盘总量、身份、装载申请或返空守恒逻辑，本轮也不运行空托盘实验。**

旧 S4 原本就用 `earliest_start(time + travel, service)` 查询 ETA 日历，正式南宁配置也已经开启邻居合流日历可见性。这两项不是本轮新增能力。

| 模式 | 相对旧版的实际变化 |
|---|---|
| `legacy` | 完整保留旅行时间、静态势、`Q + scheduled_incoming` 件数压力以及原入口/日历等待。默认不变。 |
| `eta_calendar` | 移除 `Q + scheduled_incoming` 计数罚项；串联入口等待、更新后的 ETA 和服务日历等待。正式 R3 的入口等待通常为零，因此本实验主要检验移除计数压力。 |
| `eta_flow` | 在纯日历候选上，用已经发生的局部出流与已承诺的服务完成估计服务后等待。固定 EWMA 系数 0.25，不调参追逐结果。 |

这是对拥堵成本的候选替代实验，不是证明旧评分必然错误，也不是补齐真实设备空间阻塞模型。`target.queue` 仍表示完成服务后等待下一跳的抽象队列，不能再把它解释为服务前队列。详细公式与近似限制见 [实现说明](../../../docs/g31_ics_circulation/S4_WAIT_ESTIMATOR_CANDIDATE_20261023.md)。

## 输入、分母与统计起点

- 仅南宁地图，1×，无故障，速度 2 m/s，151 个节点、227 条边；观察终点 98,259 秒。
- 全量 28,506 个业务 ID、43,603 个运输段；所有实验组均完成 43,603/43,603 段，不删减困难任务。
- 主要统计单位为独立调度的运输段。均值、P95、P99 都使用全部 43,603 段，而不是完成子集或按业务袋求各段之和。
- “规范到达→完成”从 canonical `pass_time` 起算；“实际释放→完成”从运行中的 release 起算；另分开记录实际进入/成功规划时刻。
- 原生 Java 基线来自同日已经完成的原项目 1× 实验。本轮核验原项目 15 个 Java 文件、地图、任务、执行状态和结果文件的哈希后复用，**未重新执行 Java**。六个 G31 组均为本轮实际运行，同一个新编译的原生模块。
- 输入逐项一致性、源码和二进制快照、逐段结果均保存在各运行目录。六组 G31 仅允许评分开关不同；同释放组再精确替换为 Java generator 的 `release_epoch`，不使用搜索成功时刻代替释放。

|---|---:|---:|---:|---:|---:|

纯日历候选相对旧 G31 平均改善 **3.07%**，P95 改善 5.45%，P99 改善 6.74%；P50 则增加 0.66%，并非每个分位都改善。出流估计候选平均改善 **1.70%**。三组 G31 的源端等待均值分别为 7.742、7.749、7.748 秒，主要变化发生在进入后的阶段。旧模式已与存档二进制的结果逐段核对：**43,603 段的全部原有 bag 字段完全一致，差异数为 0**，见 [回归回执](g31_legacy_001/legacy_exact_regression.json)。

## 使用相同 Java 释放时刻的结果

所有 G31 段都使用与 Java 对应段完全相同的 generator 释放时刻，保持原 OD、任务身份、基础节点时间和其他执行参数。

| 版本 | 释放→完成平均秒 | 释放→完成 P95 秒 | 释放→完成 P99 秒 | 规范到达→完成平均秒 | G31 原生调用秒 |
|---|---:|---:|---:|---:|---:|
| 原生 Java HCA | 292.92 | 532.00 | 641.00 | 3,227.99 | — |
| 旧 G31／legacy | 224.23 | 329.67 | 485.00 | 3,159.31 | 39.48 |
| G31／eta_calendar | **223.31** | **329.20** | **480.55** | **3,158.38** | 37.78 |
| G31／eta_flow | 223.35 | 329.94 | 480.55 | 3,158.42 | 37.73 |

纯日历候选比 HCA 平均少 **69.61 秒／23.77%**，P95 和 P99 也较低；比旧 G31 少 **0.93 秒／0.41%**。这说明本组数据下 G31 原有优势仍在，新评分增益较小。

同释放并未抹去源生成延迟：若仍从 canonical 时刻计时，三组都包含共同的约 2,935.07 秒。纯日历候选的“实际释放→进入”均值约 0.0012 秒，进入后为 223.3047 秒；Java 对应为 4.0236 秒和 288.8968 秒。这是阶段耗时的描述性分解，不能将余下差异全部归因于某一个评分公式。

## 误差审计、规则边界与结论

出流估计在自身原释放运行轨迹上，已提交跳转后的服务后等待 MAE 为 7.493 秒，同一批访问的旧队列件数代理为 8.501 秒；但 RMSE 为 139.183 秒，劣于旧代理的 65.540 秒。流量近似有较大的尾部误差，不能只依据 MAE 宣称全面更准。纯日历模式的服务后预测恒为零，其误差不是服务日历预测误差。统计只评价已提交跳转、且已观测到离开目标节点的访问，不能覆盖所有候选、未提交 J2 等待或未结算访问。

在同释放运行中，出流估计 MAE 为 1.257 秒、RMSE 为 39.204 秒，同运行旧队列代理分别为 0.459 秒、5.515 秒，两个误差指标都更差。四个新模式运行的已提交预测均结算完毕，截尾数均为 0；这仍不消除不同选路轨迹的样本选择差异。

下列差异在本轮保留并明确记录，不能声称严格同语义复现：

1. Java 对非终点预约使用闭区间冲突，端点相等也冲突；G31 日历允许首尾相接并使用 `1e-9` 容差。
2. 两侧都是到达目标节点完成，不额外等待终点服务；Java 以 1 秒周期观察并推进节点报告，G31 使用连续事件时间。
3. Java 预先搜索并预约完整路线，失败时在源端重试；G31 逐跳决策并通过 J2 获得下一节点许可。同释放实验保留这些算法及执行差异。
4. EBS 入库、出库段沿用双方原有独立调度。原释放的旧 G31／calendar／flow 分别出现 12／9／10 个出库早于入库的业务因果异常；Java 与三个同释放 G31 均为 1,102 个。因此业务端到端及 deadline 数字仅作为观察指标，不能据此声称全部业务链路因果有效。主表使用完整运输段分母。

规则和原始源码证据见 [独立规则审计](../../../docs/g31_ics_circulation/FENG_NATIVE_WAITING_RULES_AUDIT_20261023.md)。

**本轮保留旧 G31 默认，新增两个可切换候选；优先保留纯日历候选用于后续验证，不把更复杂的出流估计升级为默认。** 本次单份南宁 1× 数据支持平均和尾部改善，不代表跨地图、多随机样本或真实设备空间容量的结论。
