# P2 跨tick执行：保留真实归属，也核对滚动重规划

任务书§7.3明确允许从有效计划或本轮重新求解的计划提取建议，并根据状态更新后续计划。P2要求“多盘建议跨多个tick逐步兑现”，没有额外规定两次提交必须使用同一plan_id。因此`FINAL_CONTRACT_GATES_005.md`中“同一计划跨tick两次真实提交”应保留为更细的诊断计数，不能被升级为用户没有规定的独立验收硬门槛。零同plan_id双提交不等于没有滚动跨tick执行；反过来也不能把新计划订单回填进旧计划。

source005/P2203/TF-B1-60存在下列实际案例。证据报告为`final_science_005_resumed_001/P2203_TF-B1-60_behavior_timing.json.gz`，SHA256 `6d012a16bbe3d410830c8ee59474c06af350753c9e6695ed0aa2f9ee0611b7d3`。报告绑定的decisions文件在读取前核验SHA，真实提交/接收来自其审计后的生命周期，不能把发单前decision中的`actual_submission=null`误当未提交。

9720秒的计划 `a9de603b7913c12e5b683c8473408dbefc16f664631d56049a7952b52e68d0f9` 原始费用顺序为136→57、92→95。按任务书首动作精确复核后，另存的`execution_dispatch_profile`改为：

|真实盘及方向|执行建议提交|执行建议到达|实际提交|实际接收|
|---|---:|---:|---:|---:|
|initial:92:0，92→95|9720|10006.453|9720|10006.453|
|initial:136:0，136→57|9780|10041.703|9780|10041.703|

两笔均由owner:system_domestic在不同60秒tick发出、接受并接收，分别对应request `live:21:owner:system_domestic:transfer:84` 和 `live:21:owner:system_domestic:transfer:85`。第二笔来自9780秒重新求解的计划 `64959082e455af57f96c16f460e573d112cbf5a5402f4f5e9f68edc18d0f0d83`，重新验证后其盘/来源/目标/提交时刻与前一执行建议一致。原9720计划仍只计一笔真实订单。

这个案例支持存在“建议序列—当前提交—下一tick重新规划后提交—两笔真实接收”的滚动执行链，不证明旧计划对后来命令具有持续授权或独立因果作用，也不将两次提交挤到同一tick。原始`dispatch_profile`与精确复核后的`execution_dispatch_profile`必须分开：前者保留求解器近似顺序，后者是本例对应真实首动作的建议顺序。后续时间统计使用哪个profile须明示。

另一个9900秒多盘计划的后续建议26→24，在9960秒重规划后实际改为26→49，不能计为原目标24的兑现。P2201还有建议延后、改变目标和长尾接收案例。以上正反案例都保留，不据本例宣布全部P2风险覆盖、严格无损害或科学晋级。
