# map2 1×：固定南宁候选后的第二张地图验证

日期：2026-10-23。研究口径：**原生 Java 无显式线路存储容量抽象下的比较**。

**G31 在 map2 同释放对照中仍优于原生 Java HCA，但本次新评分没有稳定优于旧 G31。** 使用相同 Java generator 释放时刻，Java 平均每段 194.643 秒，旧 G31 为 169.587 秒，两个候选均为 169.559 秒。候选比 Java 低 12.887%，比旧 G31 仅低 0.016%。保留各自源释放规则时，新候选反而比旧 G31 稍慢。默认继续为 `legacy`，本轮不据此替换成熟策略。

## 实验范围与固定参数

- map2 原始拓扑，54 节点、69 条有向边；1× 全量 28,506 个业务 ID、43,603 个运输段：13,409 direct、15,097 storage_in、15,097 storage_out。
- 全边速度 2 m/s，无故障，无空托盘，不新增线路容量、有限节点缓存或容量满载回压。保留基础节点时间、逐跳选路、J2 仲裁、原源端规则。
- map2 的 EBS 入库终点为 47、出库源点为 52；没有沿用南宁的 53/53。源 52 原服务为零，旧 G31 的 0.001 秒下界保持不变。
- 共同窗口 8260–98259 秒，Java 执行 90,000 个整数周期；G31 事件上限 60,000,000。七组全部完成 43,603/43,603 段及 28,506/28,506 个业务，未完成、EBS 因果异常、观察到的业务超期均为 0。
- Java 本次核验并快照 15 个原始 Java 文件，从原项目直接编译运行原算法及外部观测包装器；实际编译命令显式包含 9 个 App 源文件、1 个 ICS_GUI 源文件和观测包装器。运行前后原源码哈希一致，map2 结果来自本次实际运行。
- 六组 G31 使用与南宁实验相同的二进制，SHA256 为 `7260288ed0996ad01d445cbf906010faabba1a0bc531f8ba13d6c1d1dd63bb28`。没有根据 map2 结果调参、重编译算法或选择性重跑。
- 规范任务为 `data/processed/tasks/inputdata.jsonl`，SHA256 为 `968d2c876fcbf03c5b25c8e865ccd469431af3ddbf59dc9ebe073752bd93678f`。南宁任务是此客流的 OD 投影；两图使用相同业务身份与时间表，**不是两份独立随机样本**，本轮只能称固定参数的地图迁移验证。

## 本轮修改的实际含义

旧 G31 已有 ETA 日历查询，正式地图配置也已开启合流日历可见性。本轮没有重复实现这些能力。

| 模式 | 实际差异 |
|---|---|
| `legacy` | 保留旧旅行时间、势函数、`Q + scheduled_incoming` 件数压力及入口/日历等待；仍为默认。 |
| `eta_calendar` | 移除旧件数压力，串联入口等待、更新后的 ETA 与目标服务日历等待。正式 R3 的入口等待为零，因此主要验证移除件数压力的影响。 |
| `eta_flow` | 在纯日历候选上增加基于已发生局部出流和已承诺流入的服务后等待近似；EWMA 系数固定 0.25。 |

评分没有延长基础节点服务时间，没有增加容量，也没有改变空托盘身份、总量、装载申请或返空守恒逻辑。服务后队列仍是等待下一跳许可的抽象状态。实现、近似限制与测试见[候选说明](../../../docs/g31_ics_circulation/S4_WAIT_ESTIMATOR_CANDIDATE_20261023.md)及[独立审阅清单](../../../docs/g31_ics_circulation/PRO_REVIEW_CHECKLIST_20261023.md)。

## 保留各自原释放规则

主表以全部 43,603 个独立运输段为分母，从共同 canonical `pass_time` 到完成计时。Java 的源生成相对 canonical 平均延后 107.338 秒，因此此表包含源释放策略差异，不能单独归因于选路。

| 版本 | 平均秒 | P95 秒 | P99 秒 | 最大秒 | 记录的计算墙钟秒 |
|---|---:|---:|---:|---:|---:|
| 原生 Java HCA | 301.980 | 1055.900 | 1787.980 | 2101.000 | 222.93 |
| 旧 G31／legacy | **193.523** | **340.501** | 426.990 | 552.580 | 18.48 |
| G31／eta_calendar | 193.747 | 340.715 | **426.967** | **551.751** | 20.36 |
| G31／eta_flow | 193.771 | 340.664 | **426.967** | **551.751** | 18.78 |

纯日历候选比旧 G31 平均增加 **0.2245 秒／0.1160%**；出流候选增加 **0.2478 秒／0.1280%**。P95 也略增，P99 和最大值略降；不能只选尾部改善来称候选整体更好。三组 G31 实际释放与 canonical 相同，源端等待均值均为 5.6365 秒，进入后均值依次为 187.8864、188.1110、188.1342 秒。

## 使用相同 Java 释放时刻

每个 G31 段的释放时刻精确替换为对应 Java 段的 generator `release_epoch`，没有用成功规划时刻代替，也没有改其他任务字段。下表的均值与分位直接由逐段 `finish - release` 重算，不能将 canonical 分位减去平均源延迟得到。

| 版本 | 实际释放→完成平均秒 | P95 秒 | P99 秒 | 最大秒 | canonical→完成平均秒 | G31 原生调用秒 |
|---|---:|---:|---:|---:|---:|---:|
| 原生 Java HCA | 194.643 | 339.000 | 344.000 | 540.000 | 301.980 | — |
| 旧 G31／legacy | 169.587 | 270.001 | 274.001 | **293.001** | 276.925 | 16.65 |
| G31／eta_calendar | **169.559** | 270.001 | 274.001 | 295.001 | **276.897** | 17.00 |
| G31／eta_flow | **169.559** | 270.001 | 274.001 | 295.001 | **276.897** | 17.44 |

候选比 Java 平均少 **25.0834 秒／12.8869%**，P95 和 P99 也较低；比旧 G31 仅少 **0.02778 秒／0.01638%**，且最大值由 293.001 增至 295.001 秒。两个候选在这组数据上的完成时间指标一致，不能据此说它们的预测公式等价。

源等待可加分解如下。共同的 generator−canonical 均值是 107.3375 秒；Java 成功规划前等待 1.3627 秒，规划后至完成 193.2800 秒；同释放 G31 的入网前等待均值为零，入网后时间即表中实际释放耗时。这是描述性时间分解，不能把剩余差值全部归因于评分公式。同释放 canonical 指标仍包含共同源生成延迟。

## 误差、等价与统计边界

本图四个候选运行的提交后预测均已结算，截尾数为零。出流候选在原释放轨迹上的服务后等待 MAE/RMSE 为 **0.804/20.618 秒**，同一批访问的旧队列代理为 **0.362/2.390 秒**，两个误差指标均更差。同释放出流候选 MAE 为 0.0675 秒，较旧代理 0.1610 秒低，但 RMSE 为 0.7352 秒，较旧代理 0.5958 秒高，仍不支持全面更准。这里只评价已选中并提交后、能观测到离开的目标节点访问，不是所有候选评分准确率；纯日历模式的服务后预测为零，其误差不能解释为日历预测误差。

旧 G31 等价验证另行加载历史二进制，将相同完整请求仅切换模块路径后实际运行；新 `legacy` 与旧二进制的 **43,603 个完整 bag JSON 对象全部相等，差异 0**，未排除字段。见[历史等价回执](historical_legacy_exact.json)。这支持本次默认模式没有改变既有结果，不代表所有未测试场景已形式化证明。

两侧规则仍有以下已知差异：Java 非终点预约采用闭区间冲突，G31 允许相接并有 `1e-9` 容差；Java 以整数秒推进和观察，G31 为连续事件；Java 完整路线预约，G31 为逐跳许可；G31 保留既有最小服务时间。两侧均到达目标即完成，Java 完成统计使用实际完成记录，不使用末节点预约区间尾端。没有将本轮称为论文全部约束的严格复现。详见[规则审计](../../../docs/g31_ics_circulation/FENG_NATIVE_WAITING_RULES_AUDIT_20261023.md)。

Java 有 21,911 个段的 generator 释放比小数 canonical 时刻早不足 1 秒，最大为 0.99999 秒；来自原整数秒生成机制，未静默裁剪，见[源延迟与边界审计](java_native_1x/source_delay_and_time_boundary_audit.json)。map2 全部 15,097 个 EBS 两段业务满足本次记录的入库完成先于出库入网；实验仍沿用独立排程，不据此声称已新增 EBS 依赖约束。业务端到端均值包含储存等待，应与运输段分开：Java 为 2660.892 秒，旧 G31 原释放为 2505.233 秒，calendar 原释放为 2505.122 秒，同释放 calendar 为 2629.152 秒。

计算墙钟只记录本次单次运行：Java 为整个包装器运行边界，G31 为 native 调用、排除后续序列化。没有据此报告跨语言 CPU 加速比或统计显著性。

## 与南宁合读及策略取舍

| 对照 | 南宁 1× | map2 1× |
|---|---:|---:|
| calendar 相对旧 G31，各自原释放，平均时间 | 降低 3.074% | **增加 0.116%** |
| calendar 相对旧 G31，同 Java 释放，平均时间 | 降低 0.414% | 降低 0.016% |
| calendar 相对原生 Java，同释放，平均时间 | 降低 23.766% | 降低 12.887% |

G31 的原有优势在两张地图同释放对照中都保留；本次候选的新收益依赖地图和释放规则。**保留 `legacy` 默认，将 `eta_calendar` 作为可选消融；不将更复杂的 `eta_flow` 提升为默认，也不宣称本次已经取得普遍优化。** 两图各一份固定客流、单次无故障 1× 实验，不覆盖更高负载、其他速度、故障或空托盘情形。[南宁完整报告](../g31_feng_alignment_20261023/REPORT.md)保留原始结论与 EBS 异常说明。
