# C00 源合同与新业务投影可行性审计

本审计只读源工作簿、固定 profile、已冻结 C00 输入和业务 crosswalk。未修改图、容量、映射、输入、模型或 native，未启动运行。`audit_source_contract.py` 使用标准库独立检查，详细来源 SHA 和计数见 `report.json`。

## 零容量的真实来源

`map_nanning/附件：拓扑结构示例2.xlsx` 的 `邻接表!A7:F7` 是 ICS103→ICS104，即运行图 97→98。C7 距离为 0.6 m，D7 速度为 2 m/s，F7 缓存值为 0。F7 是共享公式，锚为 `F5=FLOOR(C5/2,1)`、范围 F5:F36，因此展开为 `FLOOR(C7/2,1)=0`。它不是空单元格，也不是 Python 把缺失数据变成 0。

两个源工作簿共 227 条边的端点、长度、速度、容量均与 profile 精确一致，全部容量也等于距离除以 2 m 后向下取整。profile 将容量原样保存；最早 legacy map 仅把它作 metadata。新的有限容量原生合同把该 0 解释为不可占用边，C00 同样原样执行。没有证据支持将 0 改成 1，也不能把该公式推导值称为已经核实的现场封路事实。若要改变短于托盘长度的边如何占用资源，需要设施语义或源作者补充证据，并另立物理合同。

## 业务投影遗漏的约束

`run_g4irsf31_nanning_workload.py::_balanced_assignment` 只按完整历史组大小均衡分配角色候选。`build_original_projection` 分别分配入口 lane、整 flight 的卸点和中转入口，没有检查正容量有向可达性或空盘回路。`_service_aware_distances` 选择 storage proxy 时也包含零容量边。因而它原先用于 routing-only 工作负荷的可行性，不能直接证明有限容量循环合同下的可行性。

C00 的 4,001 件、48 个完整 flight 组被映射到 99/101/103/106/108/110，合法 loaded 路径不存在。固定正容量图中，包含 storage53 的主强连通分量有 134 节点，含 36 个卸点、10 个入口。保持图容量时，这 36 个卸点与 10 个入口之间都有双向运输路径。

另有不能靠目标替换消除的问题：loader92（DU36/ICS98）是单节点强连通分量。能到达它的只有 92、98–111、131，且没有任何可从 92 到达的卸点能返回 92。原 22 盘中只有初始在 92 的 2 盘处于这个上游集合。因此保留原 92 入口时，它的 3,102 件业务至多有 2 件可能获得托盘，至少 3,100 件不能完成。该入口来自三个完整 legacy lane：B2/start2 共 1,848 件、D1/start3 共 862 件、A1/start2 共 392 件。只修 4,001 个目标不足以构成全流循环实验。

## 可供登记的新业务合同建议

反馈第 1 节允许更广业务域新增版本化场景；第 5 节要求沿用固定机场图、保留代理状态与参数。本建议可作为这个范围内的新研究业务投影候选，不能追溯修订 C00/C10 或声称同场景算法增益。若要求旧 151 节点业务 OD 逐字不变，则该方案不适用，原场景阻塞应保留。

一个最小、显式且不按完成效果选优的静态替换表是：

- 原入口 92 → 同为 domestic standard loader 的 95，三个 legacy lane 均整体保留。
- 原卸点 99/101/103/106/108/110 → 同为 domestic unloader 的 114/116/118/120/122/124，六对一一替换，每个 flight 仍为完整同一卸点。
- 其余 24,505 件的原目标不变，原来不在入口 92 的业务入口不变。

静态检查对完整 28,506 件逐件执行后，4,001 件改变 destination，3,102 件改变 origin，两者重叠 430 件，合计 6,673 件有 OD 字段变化。全部身份、到达时间、STD/期限、storage53 与释放时间、加载/卸载服务及其余 job 字段不变；全部非 job 输入字段、151 节点、227 边、容量、FIFO、headway、22 盘及其初始位置不变。360 个 flight 组与原 lane 完整性保留。所有 loaded 分段均有正容量路径，各使用卸点可返回全部 10 个使用入口。

这只是一个可审阅的确定性候选；审计没有导出可执行新输入，没有选择实际效果更好的映射。它将入口 95 的总业务数增至 6,124，一些卸点负载也增加，有限缓冲与 FIFO 仍可能造成新堵塞。可达性不能证明吞吐、时限、接收权限或无 gridlock。

若后续采用，须新建业务合同/manifest/源版本和基线；各算法共享同一完整输入，从物理 0 开始保留共同 warmup 与跨窗未完成状态。运行评价继续覆盖全部 28,506 件、所有 ACK/实体守恒及逐件参照。航班 role mapping 也应另行版本化到实际使用入口或明确保留 unknown，不能沿用旧均匀先验后暗称它与新入口投影精确匹配，也不能给 actor 加入完整历史组大小。
