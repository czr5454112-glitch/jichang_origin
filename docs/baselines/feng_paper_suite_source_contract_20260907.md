## 4. 故障发生、通知与在途改路

F2 第 29 页写故障持续整个一天周期，并说线路标为中断后从图中移除，在途袋可能绕行或停住；**没有给出这 16 个场景的首个通知 epoch、通知延迟，也没有说明先发出旧路径、再在运营中突然告知。** F2 第 18 页 Steps 6–7 / 第 20 页与 F1d P184–192 提供一般机制：读取设备信息、识别传播集合 D、更新图、暂停 D 上的袋、为还有时间改变路线的袋重规划；恢复后把暂停任务重新入队。

原 Java 可确定的范围如下：

- `RUN/Main.java:54,63–70` 从 epoch=8260 开始，每轮先生成事件，再调用 `ICS_path_finding`。
- `App/Tasks.java:129–145` 根据 `edge.isFault()` 或概率写故障 / 恢复事件；GUI 可以手动标记边。本次未找到把 16 个工作簿场景与点击时刻、通知日志绑定的自动 driver。
- `App/ICS_PathFinding.java:318–395` 确有在途处理：当前首边中断则保存暂停路线；后续故障边按时间条件加入重规划集合，尝试从下一节点重规划，失败时递归扩大故障边。
- 原 `Map.java:32` 从头部第四字段读取 `fault_threshold=4`。代码用 `ETA−now < threshold` 选重规划，论文却在“没有足够时间”暂停之后写“超过 / beyond t0”（F1d P188、F2 第 20 页 Step 4）。代码和文字不构成一致的、已恢复的阈值合同，不能把其行为不加说明照搬为论文精确实现。

因此，协议可以公开选择 epoch=8260 首轮通知、无恢复，作为全日故障的操作方式；若在首批规划之前通知，应称“首次规划即已知的全天断线适应”。**要证明运行中重规划，须另有已规划路径后才通知的有界例子，并保留原路径、通知时间、当时位置、改后路径和暂停状态。** 该例子是新验证，不应冒充论文已公开了同样通知时刻；本审计没有运行它。

## 6. 可以采用的表述
