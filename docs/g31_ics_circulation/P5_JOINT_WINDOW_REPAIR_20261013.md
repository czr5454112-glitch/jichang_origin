# P5 分支 C：实际联合返供候选、长线反证与观测后修复

本轮实现了可执行的有限联合候选求解和真实观测后的一轮修复，并完成原生分叉验证；随后在独立声明的合法返程合成因子上完成62条持续控制分支及真实同盘 P→D0 服务。结论仍是 **research_candidate，未形成新方法收益证据**。普通强窗口和观测后一轮反馈已经解释本组结果；不得把“联合”“版本”“更多测试”当作创新。

## 代码与权限

`joint_window_repair.py` 从一个合法 owner 观察出发，使用与既有解析控制相同的释放预测、源 FIFO/库存保护、公开需求和候选对。最多两个可授权供给，对已有等价需求列枚举全部部分单射指派；每对只有点估计、公开条件窗移位、再加一个最长入边接收占用跨度三种时间。原生 G31 继续负责全部物理过程、S4 路径、接收和导出授权。每场域有31个动作，包含 WAIT。**这是单边界、静态最短路径提案和三格时间的有限等价列域，绝非整个 circulation 的连续时间完整域。**

提案显式记录源盘、源 owner 版本、业务/终点腾位需求、公告版本和资源合同。实际提交同时复核版本、时钟和完整合法 public projection 的 canonical SHA256；后者覆盖尚未反映到 owner 事件计数中的 pending pledge 与取消。完整公开投影是保守读集，可能过度失效；未证明是最小读集，也没有原子多 owner 提交。批内仍逐次执行 native 请求，部分拒绝/unknown 保留。

条件占用包含入边开始至下游离开的接收占用、边容量和入口 headway 尾窗，不能只算到达后的停留。其缺口明确保留：当前本地占用、既有硬接收权/在途义务尚未完整时间窗化，远端接收时长、未来源队列、实际 S4 路径和预测误差也未闭合。因此“无条件窗冲突”不是硬可行证书，有条件冲突的候选也全部进入 native 参考，没有把预测冲突当作真实不可行而删掉。

`joint_window_feedback.py` 进一步实现真实源状态改变后的修复：仅在观察到已计划盘的下一次释放位置变化后，撤销本控制器仍 pending/undelivered 的软意图，冻结仍有效的原返供分配，再求新的时刻并由 native 复验。拒绝覆盖硬权利；失败返回 partial/unknown，不假装原子成功。没有删业务、改边、加盘、改变 FIFO 或取消已出发盘。

## 发现并修复的正确性问题

1. 同刻 pending 转运提交/取消会改变供给读集，但 native owner 事件版本和时钟均可能不变。独审指出后，逐字保存旧实现；`p5_read_set_before_001` 实际加载旧源码运行，两个用例均错误提交，`--require-fixed` 退出1。`p5_read_set_after_001` 两用例都准确返回 `stale_read_set/public_dependency_changed`，不再修改物理状态。该修复没有被计为创新。
2. 5km 接收窗的浮点相接曾产生1 ULP重叠，导致保守候选误删。修复使用向未来 `nextafter` 构造微小合法空隙，容量比较仍精确，未放宽断言；开发002保留原失败。
3. 终点腾位是本地压力需求，没有远端消息的 `demand_observed_at`；现明确使用本地观察时刻和独立需求类型，避免 KeyError。
4. `:.12g` 动作ID可能把不同时间合并，改用 `float.hex`。同时发现不能用 opaque ID 字典序作策略 tie-break，否则编码格式会改变同成本托盘次序；现用数值 `(supply, demand, departure)`。main002与feedback001相同实际请求的物理结果完全相同，差异来自策略 tie，不是分段 advance 缺陷。旧版本结果全部保留，最终比较使用main003/feedback002。

最新 `p5_joint_window_tests_004.xml` 实际19项通过，0失败、0错误、0跳过；涵盖真实同刻新 pledge/取消、长入边接收权、过期读集、不原子部分拒绝、预算 unknown、极大时间ID、终点压力、真实新源观测后修复和 no-op 条件，另验证新循环因子不改旧吸收图、共同继续不重复初始控制且实际复用 TP。旧 `tests_003.xml` 的17项回执保留为历史，未覆盖。

新循环因子增加的是执行闭环和强比较证据，不是方法创新。后续仍须记录实际触及 owner/资源与完整计算；本实验不放行P6大训练、未证明完整100ms，也不替代原图业务和TRE/CIE门槛。
