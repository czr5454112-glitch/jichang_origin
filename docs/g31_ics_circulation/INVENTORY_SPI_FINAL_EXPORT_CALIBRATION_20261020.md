# 成对采集前的最终导出校准

runtime004 的两条旧 P901 诊断均已到达原物理终点 59400。完整证据导出
仍有明显资源开销：先观察全部 ACK 会同时保留原生历史、完整客户端历史
及 ACK 视图；两进程导出期间主机可用内存曾约为 0.4 GB。逐标量 Python
JSON 编码的实测 ACK gzip 增长约为每分钟 18 MB。训练配对、拟合及新正式
测试此时均未启动。

最终导出统一采用以下纯 evaluator 实现校准，保持原控制流程与科学合同：

1. 首先完整写入并关闭 controller_final_state，随后释放 worker 中 state
   和 run 两个整状态引用，再按原 owner 顺序观察 ACK。全部历史仍在原工件
   中，后续标签计算只用 calls、final、planner trace 与 ACK。
2. JSON 前三层容器保持顺序逐项写出；每个更深子树使用标准 C JSON 编码。
   这避免同时构造整日 JSON 字符串，并减少逐标量写入。该方法不承诺固定
   字节上限；记录实际最大编码子树。gzip、数字、键转换、Unicode、异常
   和禁止覆盖的语义保持原样。
3. 使用冻结的新公共源码供全部首轮/第二轮配对和正式五组。旧 runtime004
   诊断及未启动计划保留，并明确源版本差异。原公共底座、候选目录、信息、
   参数、标签和完整物理窗口均不据此次旧诊断结果调整。

纯测试核对精确 JSON 字节、合法共享引用、循环与非法数值拒绝。两条
runtime004 闭合且释放内存后，另外对保存的真实完整状态做离线重编码
字节核对，并记录实际耗时与最大块；这些检查不启动原生会话。
状态所有权的实际长窗口一致性仍由 runtime002/004 全量对照验证，
不得将仅纯测试或源码意图当成已通过的实际一致性证据。

原 16 小时、128 长分支、24 短门禁、并发最多 2，以及 2280/2400 秒
单分支软/硬上限均不变。失败、超时与此前未启动版本全部保留。
