# Original-flow second supply: bounded preparation

The separate `research_original_low_wip_reuse.py` experiment extends the successful `original_low_wip_prepare_005` experiment by at most one physical supply request. It does not modify that experiment, the native026 binary, original jobs, permissions, capacities, FIFO, or physical admission rules. Preparation and pure tests do not establish an actual second completion.

The first phase inherits the frozen005 `Owner` implementation. All 22 startup parking transfers and the first supply use that implementation. A saved-data test replays the authentic005 API tape through the first supply at physical time8890, checking every call, argument, response and clock; it stops before any new phase. The first job identity is selected by the original online rule, not hardcoded by the extension.

After the first supply, each owner still refreshes its own outstanding requests. The original token owner checks only its own current local view. It publishes a native v2 invitation only when the first transfer has a delivered `received` ACK and the same token is again locally empty, stationary, available, and not reserved for reception. This avoids continuously publishing full snapshots during the loaded trip.

The peer queries its own received v2 endpoint. A reply requires a delivered source snapshot containing the returned empty token, a source-local destination completion receipt for that token, and the first transfer's received ACK. That condition only permits a new native snapshot reply; it does not authorize a physical action. Static node contracts used for validating those messages come from the peer's own native observation.

The token owner must then possess its own final ACK carrying an immutable v2 self-copy with the exact first job's `UNLOAD_COMPLETE` receipt. It also rechecks the current local token is empty and available. The self-copy is selected by its newest known publication sequence before checking expiry, so an expired newest copy cannot revive an older one. It chooses the second supply from the latest delivered peer snapshot, considering only the earliest waiting job at each source under native arrival/identity FIFO. An unreachable head is never skipped within its source. There is no same-owner fallback, extra carrier, route override, or use of another owner's private observation.

Only one second-supply identity can be created. The source stops new publications after submitting it. Once the peer sees that actual submitted action in a delivered source snapshot, a sticky flag stops new peer publications even after that snapshot expires. This is a conditional stop rule, not a claim that delivery has already happened. Without that observation the peer may reply while the last invitation remains valid, then stops when it expires. ACK and retry processing continues.

The predeclared limits are 24 unique physical requests (22 parking plus 2 supplies), 22 original trays, all 28506 original input records, horizon 28800, 10-second observation ticks, original 2-second command/publication delay, and 120-second snapshot validity. A shared 600-second parent budget begins before execution-time preparation, pin review and the exclusive claim. The native child and the separate pure saved-data verification child each get only the remaining time. A timeout, verification failure or observed total deadline exceedance is unknown even if physical receipts already exist. OS scheduling and final receipt publication are not a real-time guarantee. All API rows and failures remain saved. This is a single bounded candidate, with no parameter or outcome screening.

Acceptance requires two distinct jobs' actual `LOAD_START`, `LOAD_COMPLETE`, `UNLOAD_COMPLETE`, and `HOLD_COMPLETE` events on the same token in order; the first hold must finish before the second supply. Exactly those two jobs may load. All24 physical requests need received ACKs, all22 parking transfers must have completed, the native horizon must be fully drained, physical audit must pass, and the token must finish empty. Missing acknowledgements, an unavailable next FIFO head, a censored horizon, or a missing second lifecycle remains unknown or unsuccessful. Per-job protection, deadline improvement, general feasibility, and complete-request100ms compliance are not established by this experiment.
