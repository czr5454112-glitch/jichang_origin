# 本轮共同执行的保守合同

合同 ID：`g31.initial_components.A_incumbent_B_queried_deviation.v1`。

本合同仅用于已声明的三个五任务有限盘研究场景，不改变原机场图、原始请求、R1/R2最终目标或严格逐件保护标准。它修复“两个安全完整方案可以任意取分量”的错误推论；尚未提供全域联合控制或异步执行保证。

## 权限和可组合域

- A 负责 `initial_action` 与 `return_delay`，本版保持公开 incumbent04 的这两个分量。
- B 负责 `empty_departure` 与 `later_action`。B 只能从自己的原选择器已查询、原方法允许、五任务预测均不差于本方 incumbent04 的候选中，选择 A 分量等于 incumbent04 的完整方案。
- 原选择器仍先按原方法执行。门保留原选择、原逻辑查询索引、被排除的受保护候选和过滤耗时；过滤增加零模型预测和零选择器查询，额外检查与诊断扫描单独列出。
- 两边不读取对方预测表、私有队列或未送达计划。上述权限域是共同的静态控制合同，不是由另一方私有提案产生的假定。

若 A 执行合同中的两个固定分量、B 执行其验证方案中的两个分量，则有效完整 vector 与 B 验证的完整 vector 相同。这是有限动作域中的结构性质。它依赖实际动作兑现，不能推出未知未来、模型误差或任意原生拒绝下的逐件保护。

机制场景保存证据中，04→12 的非默认空盘时机改善 receiver 约 0.119s，其他四件不退化；25 的更大收益被排除。12/25 的旧拼接实际形成09，使 reuse1/reuse2各延迟约0.9s。因此本版公开承担可行域损失，不能把舍弃 R1 偏离和联合25称为完成联合目标。

## Offer、请求和兑现

模型预测与本合同通过都只是条件性 offer。原生路线 ACK 表示接收路线偏好，不是硬时窗预约。固定模块的导出、接收与资源许可仍由原 native 权限检查；Python门不能授予预约、替固定模块兑现义务或绕过接收拒绝。

提交前只可修改尚未发出的本地动作；进入 `client.submit` 后即视为可能已发。既有 outbox 与创建 lineage 保留不可变 request ID 和 payload。缺 ACK、提交异常或超时不能推断未发，不能以新 ID 重派同一实物。原生允许的同 ID 重试仍使用既有机制。

后续返回和路线动作继续使用原有实际 owner/current/history/消息联合/时窗守卫。这些仍是保留初始估计的执行，不是事件触发的后缀重估。未发后缀可变域仅是本方尚未提交且通过当前守卫的动作；已经发出的前缀不在修改域内。

结构兼容还依赖A的继续策略实际存在。若A收集或预测失败，B不能把静态“A保持04”理解为A已授予承诺。修复版002的真实首格就出现A绑定失败而B已提交的状态；终态保留unknown与不可撤回身份。本合同尚没有controller存活/公开就绪协议，也不以对方策略对象的内存状态冒充已送达承诺。

## 验证与缺口

小型回归保存04、12、25、09的真实五件完成时刻和分量映射；测试覆盖旧混合两件严格退化、新门拒绝该混合、保留非默认12、拒绝未查询候选、unknown和0.001s损伤。

原生初版注册21格、先行9格，每格60s、全组600s。`compatible_initial_native_20261017_001`实际留下3格硬超时、第4格中断、其余17格未执行。超时前没有持久worker阶段或outbox，故是否已构造 native session、是否已发命令均为 unknown；不能据此判定业务或100ms成功。已修复此证据缺口，后续不同命名运行保留阶段日志、被动Python outbox快照与超时堆栈，并首次进程失败即停。

T2注册正常、单ACK延迟、部分提交后拒绝三个消息带，每带2变体，保留H40/每格60s/最多12格与720s上限。当前 native 只提供全局ACK延迟及每个请求的首包丢失配置，不能直接声称注入了“恰好一个ACK延迟”；也未给本合同提供合法部分联合提交后拒绝的注入接口。两故障带明确未执行；正常带后来获得004的真实原生九格闭合证据，但仍不满足T2整体通过条件。

继续方向是先完成真实原生9格及故障闭合，再在现有权限下扩展可执行兼容域；若确需固定模块承诺，必须显式提出接口变更，不能为恢复25而把路线ACK升级成预约。

第四格 no_overlap/incumbent 在25.39秒以Windows访问异常0xc0000005退出，非60秒超时；自动停止后余17格未执行。持久日志证明已经通过admission并进入native branch；最后partial处于A的同32预测，四条种子/规划发布请求必须保留，快照之后是否发出其他动作仍unknown。Windows事件记录故障模块python311.dll、偏移0x259cf7；20秒异步堆栈输出到`File`半行时中断，尚未得到完整崩溃符号栈。

该现象与[CPython官方3.11多线程faulthandler竞态报告](https://github.com/python/cpython/issues/116008)高度吻合，但仅作为待隔离假设，不倒推本格成功。[本机版本对应C实现](https://github.com/python/cpython/blob/v3.11.9/Modules/faulthandler.c)区分持GIL的Python同步`dump_traceback`入口与异步watchdog。下一修复仅针对诊断输出方式，保留阶段/部分证据、硬预算与业务守卫；旧003异常证据不覆盖。
