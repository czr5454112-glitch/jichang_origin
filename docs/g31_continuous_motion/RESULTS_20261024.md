## 实际修改

正服务节点统一通过时间 2 秒，原图零服务连接点保持零；同一有向边入口至少间隔 2 秒，恰好 2 秒合法。时间按整数微秒核验。放行后的相邻时间戳严格满足设备通过时间加边行程时间，没有内部等待动作。源点和终点的正服务占用也检查，业务完成后尚未结束的预约继续保留。

每个节点采用邻接候选评分；物理放行必须持有到目标的完整连续运动预约。到达内部节点时允许重新选择下一跳，只有完整新后缀通过核验才原子替换，失败继续执行旧预约。因此局部观察范围与安全协商范围分开：仅观察一跳本身不能保证任意远处无冲突。

006 在公共源端 FIFO 不变的条件下，用已经发生的重试等待放宽本件绕行许可：`120 + 1 × (当前时刻 − 首次规划时刻)`。它帮助长期阻塞的队首寻找稍长但可立即连续通过的通路；每次证书搜索仍限定 256 次展开。该规则是待实验检验的启发式，不是最优性或吞吐稳定性证明。重试时钟从不重置。

另一项独立修改省去了零拥堵权重、一跳评分时乘以零的日历查询。两图完整 005→006 零放宽对照核对了 87,206 个运输段、1,210,780 条真实事件，物理轨迹完全一致；同次配对测量的事件引擎 CPU 分别下降约 24% 和 28%。这是同实现优化证据，不是相对 Java HCA 的跨语言加速比。

选中的两图共同参数为 `fixed1_w0_cap120_relax1_006`，在观察 2× 结果之前冻结。当前选择使用静态剩余成本排序，仍进行精确预约冲突核验；它没有启用非零的多跳拥堵评分。该 w0 参数的无故障大样本中，成功中途换路次数为零，不能将其性能改善归因于实际发生的途中重规划；后续非零权重消融另列。自适应多跳与后缀交换已在单进程串行事件引擎中实现；真实设备间的通信、分布式互斥和事务协议尚未实现，也未验证实际时钟与执行误差。

## 指标与共同条件

主 THT 对每个原始业务袋，将各运输段的 `实际目标到达 − 首次实际规划` 相加。首次规划失败后转而处理下一件，其重试等待仍计入；EBS 入库、出库分段计时，不含两段之间的存储。不能改用成功放行时刻作为起点。

同时报告首次规划之前的积压、含名义释放后积压的分段总历时、固定窗口完成量及两项截止率。名义分段总历时可能因 EBS 两段名义窗口重叠而重复覆盖时间，不等于唯一业务墙钟历时。原窗口未完成时，全人口 THT 留空；另用冻结同一批输入的排空实验取得完整均值。

同一袋的 **739 个不同实际尝试时刻**，曾在更早快照中被证明具有完整短路线窗口，却在实际尝试时被此后新提交的预约阻挡。例如 34,347 秒的前缀 265856 允许 34,379 秒出发；到实际 34,379 秒，新预约 `459304`（创建序号 265858，所有者 `36394:direct`）占据节点 112 的 `[34444.85,34446.85)`，与本件所需 `[34445,34447)` 重叠。这支持“未预留的未来机会后来被占用”，不表示已拥有的权利被抢占。唯一原策略已经排定且在较早快照可行的下一次重试为 50,746 秒，实际成功。

## 010c：有限未来源端预约候选

010c 保留 006 的绕行放宽、每秒源端节奏与共同 FIFO。当前立即出发搜索因第一个静态可选分支之前的预约冲突而失败，且首次规划后已经等待至少 2 秒时，才检查固定静态短路线未来 60 秒内的整秒出发窗口；仅预算耗尽或绕行上限失败不触发。完整路线的所有节点、边入口窗口同时合法才提前提交预约。行李仍留在源端队首，约定时刻才实际准入并放行后件；这段等待继续计入 THT。它求的是该固定路线的最早合法整秒出发，不是全图最早或最优调度。

## HCA 是否允许服务节点等待

原 HCA A* 没有显式 WAIT 后继；节点碰撞会拒绝该候选，整条路径失败后任务留在待规划列表，后续再试。它并非按设计在内部服务节点任意停车排队。

但原实现更新已发现节点的父节点和代价时漏更新 `t1/t2`。真实小例复现了 10 秒不符合连续时间递推的空档。因此不能把原代码直接视为严格无内部等待；该空档也不足以定位成某个物理服务队列。当前公平基准标为“修复 HCA”：同步更新时间戳，并统一两秒半开窗口、整数微秒逐步相加、源/终点占用、边入口间隔、预约清理、稳定源序与真实 EBS 入库门。没有另改 A* 启发式和路径优先级；公共物理合法集改变仍可能改变其路线。没有把这一基准冒称为未经修改的冯算法。

HCA 首次规划取实际加入待规划列表的时刻，而非成功路径输出时刻。无故障控制循环在加入的同一 epoch 逐一尝试所有新增任务，源代码证明保存在 `hca_first_planning_source_proof_001.json`。

## 文献依据与计算开销

[Tarău 等的行李系统 MPC 研究（2009）](https://www.dcsc.tudelft.nl/~bdeschutter/pub/rep/09_024.pdf)支持事件触发、局部预测和邻居协调，但允许切换处停车，不能直接继承其安全结论。[Sohrt、Overmeyer（2020）](https://www.bvl.de/misc/filePush.php?id=52974&name=10.23773_2020_8.pdf)的本地日历、沿路预约确认和拒绝后的可用时间反馈，更接近本实现的安全协商与失败反馈思路；它没有给出这里的线性绕行公式。

G31 006 选中参数的事件引擎 CPU：1× map2 3.234 秒、南宁 5.125 秒；2× 原窗口 6.906 秒、8.625 秒；2× 全排空 8.313 秒、10.797 秒。这些时间不含静态剩余成本预处理、初始化、Python 输出和独立审计。南宁全排空源端单次尝试 p99 为 266.3 微秒，途中决策 p99 为 9.0 微秒；它们是本机仿真测量，不是硬实时最坏响应保证。

HCA 整场计时包含逐 epoch 文件读写、任务生成、解析与其它调度，未单独测出纯文件 I/O 占比。因此不得用整场 Java 数百秒与 G31 原生引擎数秒直接计算“算法加速比”。HCA 004 单独记录 A* 调用时间，CPU 只覆盖规划线程，不是整个 JVM 的所有线程；短调用的累计 CPU 还受 Windows 计时粒度影响。语言、JIT、时钟粒度与事件处理边界均有差异。
