# 原投射结构不合法时：保留原件，另建受约束投射版本

本文件为只读来源核验后的设计增补。没有执行重投射、改写输入、过滤袋或运行物理实验。原件的实际类别和数量以同目录 `analysis.json` 为准。

旧 G31 规则保持原 timetable，但装载 lane/航班目的组的贪心负载平衡没有把有向可达/空盘回流放入赋值约束。在正容量图上出现不连通或无回流 OD，不等于新控制器有算法缺陷，也不允许把那些袋删除后报告全量可服务。

两条分支应同时明确：

1. **原投射诊断分支**：原 SHA/每袋身份/时序和全部分母不变。分别报告加载段不可达、EBS 必经链不可达、可达但没有声明许可的空盘出口/回流、以及结构可达但动态资源未获授权。不能将后者都写成拓扑不可行。旧负结果继续保留，图上的禁止边不打开。
2. **新版本受约束投射开发分支**：依外审允许的“按原任务规则调整流”，在看 J 前冻结完整任务分组、许可集合和静态规则；用所有原始袋重建 OD。保持原到达/STD/早包阈值/释放规则、完整航班组不可拆、原 Loader lane 分组与转机身份，不改图、方向、mode 权限或模块业务能力。新 raw/canonical/manifest 以新 version/SHA 保存，独立于原件；仍是同一日的派生开发输入，不是新确认来源。

建议先做 **固定旧 source-lane 映射的目的端可行性库存**，再决定是否需要同时调整 source assignment。对每个完整原航班组 F，列出有业务权限的 unloader 节点 u：该组每个源点上的直接袋必须存在合法 loaded 源→u；早包须存在源→已声明 EBS→u；u 到至少一个有接收权限的空盘存储/供盘目的地须存在合法 empty 路径。若研究合同要求每个源点的闭环，则再加入该特定回流要求并标注它比“回到任一合法供盘位置”更强，不能在两者之间默换。

这只是静态必要条件。一个汇点能回到某仓库，不保证全体源点长期都有盘；后续还需共享流量平衡、 finite inventory、时间化回压/服务和实际 owner admission。不能通过把所有回盘送到一个无穷库给出可持续保证。没有现场模式许可时，只能在显式共同代理许可下计算库存；静态路径不是授权。

若某完整航班组没有任何可用目的节点，必须保留 empty feasible set 及阻断的源/阶段/权限原因。可进一步预声明 **联合 lane→loader、flight→unloader 的整数分配**，候选只在文档规定角色集合内，成本只用冻结的计数平衡/静态长度（不用控制器 J/后验 regret），完整组原子赋值。所有袋必须恰赋一次；完整分组与来源关系不变。若要求保持每个注册 loader 业务量、同区/跨区比例、原 lane 连续绑定，这些必须列为独立约束，有冲突时不能静默放松。

一种可实现的 prepare API 为 `build_projection_feasibility(source_groups, graph, role_contract, storage_contract, permissions)`，输出每组候选域与被拒原因；再 `assign_atomic_groups(feasibility, frozen_balance_objective, solve_budget)` 输出完整映射或 `proven_infeasible`/`budget_unknown`。图与模式的静态可达可以精确核对；整数求解没完成时不能把剩余组丢掉或把耗时上限称不可能。预声明确定排序/平局规则以及 objective 是仅用于场景构建的需求均衡代理，不能让它承担路由/供盘算法奖励。

已有注册 loader 若自身对所有允许卸载/EBS 都无出路，同时又要求该 loader 必须继续承担原流量，则新投射也无解。正确结论是这组输入/角色/权限合同冲突；需要新增有效来源说明或明示改变场景假设，不能私自搬走该源所有袋却仍称原业务覆盖。类似地，必须跨区但两区无许可回流时，单靠重新分配目的地不能弥补方向或模块约束。

重投射后先做纯文件全袋身份/时序/航班组/来源 lane 守恒、静态必要条件与新旧来源映射审计，再合法 burn-in/full-cycle。old 与 new projection 的服务水平不能作为同任务同条件算法改善；真正算法比较在每一个冻结 projection 内成对进行，并同时披露原投射诊断。重投射只排除研究已明确认定无意义的结构赋值，不是把困难的动态容量冲突从实验中删除。
