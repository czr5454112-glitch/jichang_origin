# G4IRSF29：2× 实验中产生的新想法与后续边界

## 1. 从“复制行李”改为“加密航班”

2× 任务流应在论文的业务生成单元上扩展，而不是复制已经展开的 route segment。G29 将完整航班 manifest 作为单位，在同一 `(end, Unloader)` 航班序列中插入中间班次，同时平移该班所有行李的 EntryTime 与 STD。这样能够同时保留：

- 航班内 source、loader、终点和卸载口构成；
- `STD-EntryTime` 与直达/EBS 分类；
- 同一原始订单的 storage-in/storage-out 生命周期；
- 原论文的一天时间轴。

这个方法适合以后构造 1.5×、2× 等容量场景：改变班次密度，不改变单件行李的业务规则。

## 2. 容量与完成时间必须分开判断

在固定 90,000 epoch 窗口内，2× HCA* 可以释放全部任务但仍留下少量未完成订单。此时：

- 固定 57,012 分母的完成数是有效容量指标；
- 只对已完成幸存者计算的平均/P95/P99 不能代表完整总体；
- 只有双方都完成全部总体时，完整时间分布才进入正式胜负。

因此本轮将 `capacity verdict` 与 `full-population timing verdict` 分成两个轴，而不是用一个平均值掩盖删失订单。

## 3. 2× 下的新瓶颈首先出现在 source release

S4 的 exact-release 主比较复用了对应 HCA* 的逐 segment release，因此它测量的是相同注入后的局部路由与合流能力。2× 时 release 相对 scheduled arrival 的等待显著放大，说明未来若要研究真正端到端容量，应单独研究 source-local admission/FIFO；不能把这类等待错误归因于 S4 路由分数，也不能通过增加全局规划层来掩盖。

## 4. 线路中断的合理终点是拓扑上限

故障场景中，删除故障边后不可达的订单无论采用何种路由器都无法完成。确定性的局部结构故障值应以“达到剩余拓扑可达上限”为目标：

- 有可恢复余量时要求严格超过 HCA*；
- HCA* 已到上限时允许 ceiling tie；
- 不为制造严格胜利而延长窗口、改变地图或把不可达订单移出分母。

这比继续微调 learning residual 更简单，也更符合当前局部决策框架。

## 5. 暂不增加新的策略层

G29 沿用 S4/J2/E2、节点局部 FIFO、service-aware static potential，以及故障时的确定性局部结构值。没有启用 DLP learning，也没有增加完整 A*、未来路线或全局预约表。若最终仍有退化，应先判断它属于 source release、物理/拓扑上限还是局部合流；只有明确证据指向现有拥堵项时，才值得对一个已有权重做一次很小的验证。

## 6. 仍未恢复的论文实现

Table 5.3 的分散启发式实现和 Table 5.4 的原动态/静态偏差变体均缺少足够源码或参数，不能重建成 fresh exact 2× 对照。它们在报告中只能作为归档或显式 reconstruction 上下文，不能驱动“fresh 2× 全科目已证明”的结论。后续若取得原实现，应复用本轮同一 2× 航班任务流重新运行，而不是根据归档均值反推参数。
